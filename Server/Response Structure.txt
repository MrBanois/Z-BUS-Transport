==========================================
Response Structure
==========================================
/api                    (GET)
    message : API is running

==========================================
Error detail shapes
==========================================
Two shapes are in use, and the difference is what the client does with it.

    plain string      "detail": "Account not found"
                      Rendered as a banner above the form or list.

    named field       "detail": {"message": "...", "field": "email"}
                      Rendered under that input instead, when the named field is
                      one the screen actually shows. Anything else falls back to
                      the banner, so a message is never silently dropped.

Only routes that build their HTTPException through errors.field_error() send the
named-field shape. Field names are the client's form keys: firstName, lastName,
email, department, position, name, permissions, password, salary.

==========================================
Passwords
==========================================
No endpoint returns password material. The listings used to include `passwd`,
which handed every account's MD5 digest to the caller; that field is gone from
both user listings and from the profile shape.

The two writes treat a password differently, on purpose:
    POST /api/user        `password` is REQUIRED. Creating an account is how a
                          credential is handed over, so the credential is part of
                          the request. A server-invented default used to stand in
                          for it, derived from the public sequential USER.ID,
                          which let anyone who could list accounts derive any
                          other account's password.
    PUT /api/user/{id}    `password` is optional. Omitted (null) means the stored
                          hash is left exactly as it was; supplied, it replaces
                          it.

The digest is MD5(id + password), so it cannot be reconstructed from the stored
value. A client therefore cannot round-trip it, which is why no read shape
carries it, and why the edit form is allowed to send no password at all.

==========================================

/api/login              (POST)
    request body :
        email: str
        password: str
    401 Invalid credentials  (unknown email OR wrong password, same detail for both)
    response :
        message : Login successful
        user :
            id : id
            name : name + lname
            email : db_email
            permission : perms   (16 bit 0/1 mask, see PERMISSION_ORDER)

==========================================

/api/register           (POST)
    Creates a PASSENGER only. Always stored with ISEMP = 'F', SALARY = NULL.
    dep and pos must reference DEPARTMENT / POSITION rows with ISEMP = 'F',
    otherwise the account cannot register a staff department or position.
    request body :
        f_name: str
        l_name: str
        email: str          (unique, stored lowercase)
        password: str       (min 6 chars, stored as MD5(id + password))
        dep: str            (department id)
        pos: str            (position id)
    400 invalid name / email / password / department / position
    409 Email is already registered
    response :
        msg : Account Created Successfully
        info : U000000016    (the generated user id)

==========================================

/api/position           (GET)
    List[Position], ordered by id
        id: str
        name: str
        permission: str      (16 bit 0/1 mask, see PERMISSION_ORDER)
        isemp: bool          (True = staff, False = passenger facing)

/api/position/passenger (GET)
    List[Position]          same shape, only ISEMP = 'F', ordered by id
    Feeds the registration form's position dropdown.

/api/position           (POST)
    request body :
        name: str           (required, trimmed, max 20 chars)
        perms: str          (required, exactly 16 '0'/'1' characters)
        isemp: bool         (optional, defaults to true)
    The id is generated here, so two administrators cannot pick the same one.
    400 empty or over-long name                (field: name)
    400 malformed mask                         (field: permissions)
    409 a position of that name already exists
    response :
        msg : Position Created Successfully
        info : P0011 (Clerk)

/api/position/{id}      (PUT)
    request body :
        name: str           (required)
        perms: str          (required)
        isemp: bool         (REQUIRED, no default)
    Full replacement, not a patch: both the mask and the account type are always
    written. `isemp` deliberately has no default, so a partial caller gets a 422
    rather than silently turning a passenger facing position into a staff one.
    400 / 409 as for create
    response :
        msg : Position Updated Successfully
        info : P0001 (Driver)

/api/position/{id}      (DELETE)
    404 Position not found
    409 This position is still assigned to N account(s). Move them first.
        Without this guard Oracle raises ORA-02273 and the caller sees an opaque
        500 instead of anything actionable.
    response :
        msg : Position Deleted Successfully
        info : P0011

==========================================

/api/user               (GET)
    List[Userdata], ordered by id. No `passwd`.
        id: str
        f_name: str
        l_name: str
        email: str
        pos: str            (Position ID)
        dep: str            (Department ID)
        isemp: bool
        salary: float
        pos_name: str|null  (null on this route, by design)
        dep_name: str|null  (null on this route, by design)
    Read every account, staff and passenger alike. No filtering flag; a client
    that wants staff only filters the response it already has.

/api/user-linked        (GET)
    List[Userdata], same fields and same absence of `passwd`, but INNER JOINed,
    so pos_name and dep_name are populated.
    Rows whose department or position is missing drop out, so this is the
    account list to use when a screen must show a name for every row.

/api/user/profile/{id}  (GET)
    The signed-in member's own record. Narrower than Userdata, and deliberately
    explicit that nothing credential-shaped crosses this route.
        id: str
        f_name: str
        l_name: str
        email: str
        dep: str             (Department ID)
        dep_name: str
        pos: str             (Position ID)
        pos_name: str
        isemp: bool
    404 Account not found

/api/user/profile/{id}  (PUT)
    A member renaming themselves. Does not touch EMAIL, PASSWORD, ISEMP or
    SALARY, and never can.
    request body :
        f_name: str          (required)
        l_name: str          (required)
        dep: str | null      (null means leave as stored)
        pos: str | null      (null means leave as stored)
    400 empty / over-long name            (field: firstName, lastName)
    400 malformed assignment id
    403 Employee department and position are assigned by administration
        An employee's dep/pos are administration-controlled, so a member cannot
        move themselves onto a different one.
    400 department not available to a passenger account   (field: department)
    400 position not available to a passenger account     (field: position)
    404 Account not found
    response :
        msg : Profile Updated Successfully
        info : U000000001

/api/user               (POST)
    Creates an account on someone's behalf.
    request body :
        f_name: str          (required)
        l_name: str          (required)
        email: str           (required, unique, stored lowercase)
        dep: str             (required, Department ID)
        pos: str             (required, Position ID)
        isemp: bool          (required)
        sal: float           (optional, defaults to 0, max 999999.99)
        password: str        (REQUIRED, min 6 characters)
    Note the body field is `sal` while the listings read `salary`. That asymmetry
    is pre-existing; both sides match the column they were written for.
    400 empty / over-long first or last name (field: firstName, lastName)
    400 email missing, over-long or malformed   (field: email)
    400 salary missing or above the column max  (field: salary)
    400 password shorter than 6 characters      (field: password)
    400 department / position does not exist    (field: department, position)
    400 a PASSENGER cannot be assigned a staff department or position
        The reverse is allowed: giving an employee a passenger facing position
        only ever removes screens, so there is no reason to refuse it.
    409 That email address is already registered          (field: email)
    response :
        msg : User Created Successfully
        info : U000000017    (the generated user id)

/api/user/{id}          (PUT)
    Full row replacement. Every column below is written every time, so omitting
    one resets it rather than leaving it alone.
    request body :
        f_name: str          (required)
        l_name: str          (required)
        email: str           (required, unique, stored lowercase)
        dep: str             (required, Department ID)
        pos: str             (required, Position ID)
        isemp: bool          (required)
        sal: float           (optional, defaults to 0, max 999999.99)
        password: str        (optional; null leaves the stored hash untouched,
                             a value RESETS it. Note the asymmetry with POST: a
                             create has nothing to keep, so it must supply one.)
    The password rule is the correction that makes this screen possible: the
    signature used to require one, and since the digest is MD5(id + password) an
    administrator renaming an account had to know its current password or
    silently destroy the credential.
    400 as for create, plus 404 Account not found
    409 That email address is already registered          (field: email)
    response :
        msg : User Updated Successfully
        info : U000000001

/api/user/{id}          (DELETE)
    404 Account not found
    response :
        msg : User Deleted Successfully
        info : U000000001

/api/report1            (POST)
    A year and the whole year only; 31 December is inside the report.
    request body :
        year: int
    422 missing / non-integer `year`, via FastAPI's normal validation
        No field errors are reachable here: a year body has no range to reject.
    response : Report, date_range = str(year)
        report_title : Station Statistics
        date_range   : '2025'
        data         : one row per station, 26 keys in this order:
            station_id : str
            Station    : str
            Pickup_January, Dropoff_January, Pickup_February, Dropoff_February,
            ... through Pickup_December, Dropoff_December   (int counts)
            Twelve months are always present per station, 0 where nothing ran,
            so a quiet month reads as zero rather than an absent key.

/api/report2            (POST)
    request body :
        year: int
    422 as for /report1
    response : Report, date_range = str(year)
        report_title : Booking Statistics
        date_range   : '2025'
        data         : one row per month, twelve rows in calendar order:
            Month      : 'January' ... 'December'
            Bookings   : int
            Seats      : int
            Cancelled  : int
            Checked-In : int
            No-Show    : int

/api/report3            (POST)
    request body :
        start_date: date   (YYYY-MM-DD)
        end_date: date     (YYYY-MM-DD, INCLUSIVE; last day included)
    400 The end of the range cannot be before its start   (field: end_date)
    422 missing / malformed `start_date` / `end_date`
    response : Report
        report_title : User activity
        date_range   : '2025-04-01 to 2025-04-30'
        data         : one row per user, ordered by name:
            User       : str   (F_NAME + ' ' + L_NAME)
            Bookings   : int
            Checked-In : int
            Cancelled  : int
            No-Show    : int

/api/report4            (POST)
    request body :
        start_date: date
        end_date: date     (inclusive)
    400 / 422 as for /report3
    response : Report
        report_title : Route Statistics
        date_range   : '2025-04-01 to 2025-04-30'
        data         : exactly seven rows, Monday through Sunday, one column per
                       route (see notes). Each row:
            Day      : 'Monday' ... 'Sunday'
            <route_id> : int passengers  (one key per route id)
        Notes. Column keys are route ids -- the screen pairs them with /api/route
        names rather than the server duplicating them. The columns are the
        active routes plus any route that actually carried trips in the range,
        sorted by id: a route deactivated mid-history keeps its column, so its
        passengers do not silently vanish.
        Every one of the seven days appears even when nothing ran, reading as 0.

/api/report6            (POST)
    request body :
        start_date: date
        end_date: date     (inclusive)
    400 / 422 as for /report3
    response : Report
        report_title : Late Trip Statistics
        date_range   : '2025-04-01 to 2025-04-30'
        data         : one row per driver, ordered by name:
            Driver_ID : str
            Name      : str
            Total     : int   (all trips in the range)
            Before_17 : int   (time_start before 17:00)
            After_17  : int   (time_start at or after 17:00)
        Before_17 + After_17 always equals Total; the client charts only the two
        halves so a driver's total is not drawn twice as tall as its own parts.

/api/report7            (POST)
    request body :
        start_date: date
        end_date: date     (inclusive)
    400 / 422 as for /report3
    response : Report
        report_title : Trips Statistics
        date_range   : '2025-04-01 to 2025-04-30'
        data         : one row per vehicle, ordered by type then id:
            Type     : str
            PLATE_NO : str
            Seat     : int   (capacity)
            Trips    : int
        Vehicles with no trips in the range still appear with Trips = 0.

    ----- shared notes on the reports -----
    All six are a single SELECT with no side effect; calling them cannot change
    the database.
    Every endpoint takes a JSON body. Reports 1 and 2 take `year` and lay out
    that year's twelve months; the other four take the date range and compare
    against `end + 1 day` internally, which is what makes `end_date` inclusive.
    There has never been a report5; the numbering is kept because it is how the
    reports are referred to everywhere else.
